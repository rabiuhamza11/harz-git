# IAE-1 CONTRACT — HARZ Interactive Artifact Engine v1 (FROZEN PRE-IMPL)

**Dad's ruling, Oct 9, 2026: Option C approved** under the one-gap-at-a-time law. This
contract is frozen BEFORE implementation. Implementation does not authorize changes to
unrelated frozen components, and promotion is NOT automatic — only after evidence.

## Capability

Native interactive artifact creation. HARZ generates working, interactive software
artifacts itself — no external model, no external creation service. First acceptance
artifact: a simple clock application. The clock is the first acceptance test, NOT the
limit of the capability.

## Laws (Dad's contract requirements, verbatim-in-intent)

1. NATIVE CREATION — the artifact is generated by HARZ's own engine (harz-artifact-
   refsyn v0.1), sovereign in-worker, deterministic. Zero external calls.
2. FUNCTIONAL OUTPUT — the clock must display the correct time, update continuously,
   and handle refresh correctly (device-clock driven).
3. DURABLE DELIVERY — the artifact receives a stable identity (request_id) and a stable
   URL; refresh must return the SAME artifact (byte-identical, sha-matched).
4. OFFLINE-FIRST — once installed/cached, the application continues working without
   internet. The artifact registers a service worker that caches it cache-first; the
   artifact contains zero external network dependencies.
5. HONEST STATUS — statuses are distinct and earned, never asserted: BUILT, TESTED,
   VERIFIED, DELIVERED, CACHED, OFFLINE. Never claim a test passed unless it actually
   ran; untested conditions are disclosed, never masked. Construction-verified (code
   audit proves the property) is recorded as construction-verified, NOT as executed.
6. EVIDENCE — every artifact receives a verifiable receipt binding request_id, artifact
   sha256, test results, and gate results.
7. ISOLATION — additive only. The sealed creation modes (image, voice, music, video,
   story, report) are untouched; their frozen batteries must stay green. No evidence-rule
   weakening, no routing changes (Chat Builder routing is a separate recorded issue,
   NOT part of IAE-1).

## Verbatim boundary

"A generated image of a clock does not pass the interactive-clock test."

## Acceptance gate (Dad's table)

| Test | Required result |
| Create clock | Valid interactive application generated |
| Functional test | Time updates correctly |
| Browser test | Controls and display work in a real browser |
| Refresh | Same artifact remains retrievable |
| Offline test | Cached clock operates without a network |
| External dependency audit | Zero external calls required |
| Regression | Existing creation modes remain intact |
| Evidence receipt | All results recorded and verifiable |

## Test battery (testiae1, frozen)

1. IAE-1 create: clock artifact generated, valid self-contained HTML, sha recorded.
2. IAE-2 functional: clock render logic evaluated at fixed timestamps — exact expected
   output (the TESTED function source must be byte-identical to the embedded artifact
   source; the creator never grades itself weaker than the judge).
3. IAE-3 controls: 12/24-hour toggle and theme toggle change the render output.
4. IAE-4 self-containment: zero external URLs in the artifact (regex audit).
5. IAE-5 refresh: fetch twice — byte-identical, sha match, stable identity.
6. IAE-6 cache path: service worker served; cache-first logic present; registration
   code in the artifact (offline is construction-verified; device offline run is a
   separately disclosed human test).
7. IAE-7 receipt: receipt binds request_id + artifact sha + test results.
8. IAE-8 isolation: frozen studio/creation routes respond unchanged (full regression
   battery runs separately and must stay green).
9. IAE-DT death tests: evidence questions ("what is the price of btc") refused at the
   IAE boundary (creation ≠ evidence, precedence law); unsupported artifact kinds
   refused honestly with the supported list disclosed; injection cannot alter the
   artifact kind.

## Status machine

created → tested → verified → delivered (real HTTP fetch 200) → cached/offline
(construction-verified at engine level; device run disclosed as pending until a human
offline field test executes it). No state is ever skipped or asserted without its event.
